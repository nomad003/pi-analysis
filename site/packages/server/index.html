这个包是什么What this package ispi-server 是远程 pi 会话的服务端一端：它接受任何 ServerListener 交来的字节连接，完成握手，核对每个请求的路由，再把调用原样交给应用——服务器级调用交给 serverServices，Session 调用交给应用打开的 RoutedSessionHandle 为这次附着发的租约。它不解析服务契约、不保存 Session；它负责的是路由、附着的生命周期、取消、订阅更新的顺序，以及关闭时的清理。pi-server is the server end of remote pi sessions: it accepts byte connections from any ServerListener, completes the handshake, checks every request's route and hands the call to the application unchanged; server-wide calls go to serverServices, Session calls to the lease that the app's RoutedSessionHandle issued for this attachment. It parses no service contract and stores no Session; it owns routing, the attachment lifecycle, cancellation, the order of subscription updates, and cleanup on shutdown.

1,958 行 TypeScript，三个导入路径：根入口 "."、Unix socket 传输 "./unix" 和测试工具 "./testing"。依赖 chord 与 pi-protocol；用到 node:crypto（attachmentId）。唯一的使用者是 coding-agent 的 experimental/ 服务器：每个 Session 跑在自己的 worker 进程里。1,958 lines of TypeScript, three import paths: the root ".", the Unix-socket transport "./unix" and the testing kit "./testing". Depends on chord and pi-protocol; uses node:crypto (attachment ids). Its only user is coding-agent's experimental/ server, where every Session runs in its own worker process.

Server、SessionRouter 与可替换的监听器Server, SessionRouter and pluggable listeners#

一句话结论TakeawayServer（server.ts）管连接、握手和请求分派；内部的 SessionRouter（session-router.ts）管托管的 Session、每个连接的附着和释放；ServerListener 只负责把已建立的字节连接交给 server.accept()。根入口用 export * 公开 errors、listener、server、types 四个模块；SessionRouter 与 ByteConnection 不公开。Server (server.ts) owns connections, the handshake and request dispatch; the internal SessionRouter (session-router.ts) owns hosted Sessions, each connection's attachment and its release; a ServerListener only hands established byte connections to server.accept(). The root uses export * to publish four modules: errors, listener, server and types; SessionRouter and ByteConnection stay private.

要点Key points

  • 监听器负责传输层的认证；实验性的 Unix 监听器不做认证，只依靠文件权限。Listeners own transport-level authentication; the experimental Unix listener does none and relies on file permissions.
  • coding-agent 的 radius-relay.ts 只用到 Pick<Server, "accept">：中继来的连接与本地 socket 进入同一个 Server。coding-agent's radius-relay.ts only needs Pick<Server, "accept">: relayed connections enter the same Server as local sockets.
  • Server.closed 在关闭后 resolve，监听器或 Session 清理失败时 reject。Server.closed resolves after shutdown and rejects when listener or Session cleanup fails.

工作原理How it works

  1. const server = new Server(host, { listeners, serverId })，然后 await server.start()。const server = new Server(host, { listeners, serverId }), then await server.start().
  2. 本机：createUnixServer(host, { serverId, path: getUnixSocketPath(serverId, dir) })。Locally: createUnixServer(host, { serverId, path: getUnixSocketPath(serverId, dir) }).
  3. onConnectionCountChanged(count) 观察连接数，onError(error) 收集诊断。Observe connections with onConnectionCountChanged(count), collect diagnostics with onError(error).

连接的五个阶段Five connection stages#

一句话结论Takeaway每条连接经历 awaitingHello → handshaking → ready → closing → closed。第一条消息必须是 hello，而且整个握手要在 5 s 内完成；finishHandshake() 检查版本、为连接建服务器级端点、发回 hello { version, serverId }，然后才进入 ready。协议错误走 failProtocol()：把 hello_error 作为最后一帧发出，再关闭。Every connection goes awaitingHello → handshaking → ready → closing → closed. The first message must be hello and the whole handshake must finish within 5 s; finishHandshake() checks the version, builds the connection's server-wide endpoint and sends back hello { version, serverId } before entering ready. Protocol errors go through failProtocol(): hello_error is sent as the final frame, then the connection closes.

要点Key points

  • 握手期间到达的请求挂在 state.handshake 之后，ready 时才处理，不会丢。Requests that arrive during the handshake wait on state.handshake and run once ready; none are lost.
  • disconnect() 只执行一次：abort 所有进行中的请求、清空订阅编码器，并行释放 Session 附着与服务器级端点。disconnect() runs once: it aborts every active request, clears subscription encoders, and releases the Session attachment and server-wide endpoint in parallel.
  • 关闭中的 Server 对新连接直接 close，不建任何状态。A closing Server closes new connections at once without creating any state.

工作原理How it works

  1. handshakeTimeoutMs 与 maxFrameLength 都是 1 … 上限之间的整数，构造时检查。handshakeTimeoutMs and maxFrameLength are integers within bounds, checked by the constructor.
  2. await server.close()：先关监听器，再关连接，最后关所有托管的 Session。await server.close(): listeners first, then connections, then every hosted Session.
  3. 自定义监听器：start(accept) 里对每个连接调用 accept(connection)，把返回的 handler 接到传输事件上。A custom listener: in start(accept), call accept(connection) per connection and wire the returned handler to transport events.

一个请求的处理Handling one request#

一句话结论TakeawayhandleRequest() 先拒绝重复的请求 id 和不合法的调用，再登记一个 AbortController；然后核对 serverId，按 target 是否带 sessionId 路由到 SessionRouter 或服务器级端点。订阅必须返回快照：Server 为它装上 ServiceStateEncoder，先发回应，再冲刷期间排队的更新。handleRequest() first rejects duplicate request ids and invalid calls, then registers an AbortController; it checks the serverId and routes to the SessionRouter or the server-wide endpoint depending on whether the target has a sessionId. A subscription must return a snapshot: the Server installs a ServiceStateEncoder for it, sends the response first, then flushes the updates queued meanwhile.

要点Key points

  • 错误回应用 toProtocolError() 映射：ServerError / RemoteServiceError 原样，ProtocolValidationError → invalid_request，其它 → internal_error。Error responses are mapped by toProtocolError(): ServerError / RemoteServiceError as is, ProtocolValidationError → invalid_request, anything else → internal_error.
  • 已 abort 的请求一律回应 cancelled；cancel 本身从不单独回应。An aborted request always answers cancelled; a cancel never gets its own response.
  • 回应已发出后才出错（例如冲刷更新时），Server 关闭这条连接：订阅流不能半途断掉。If something fails after the response was sent (flushing updates, say), the Server closes the connection: a stream must not break halfway.

工作原理How it works

  1. 同一连接上的请求并发处理；需要顺序时由应用在服务里自己排队。Requests on one connection run concurrently; apps that need ordering queue inside their services.
  2. 在服务里尊重 context 的 abort 信号，取消才会尽快生效。Honour the context abort signal in services so cancellation takes effect quickly.
  3. 退订成功后编码器被删掉，之后对该订阅的 publish 静默丢弃。After a successful unsubscribe the encoder is deleted, and later publish calls for it are silently dropped.

SessionRouter：attach 与准入SessionRouter: attach and admission#

一句话结论Takeawayattach 按连接串行（runForClient）：已附着同一 Session 就直接返回；否则 acquire()——已托管、正在打开或新打开（resolveSession + openSession）——释放当前附着、为新附着生成 randomUUID() 并向句柄取租约，最后带外推送 attachment 路由。Session 调用也在同一队列里“准入”：路由必须与本连接的当前附着完全一致。Attach is serialised per connection (runForClient): if already attached to that Session it returns at once; otherwise acquire()s it (hosted, opening, or freshly opened via resolveSession + openSession), releases the current attachment, generates a randomUUID() for the new one, takes a lease from the handle, and finally pushes the attachment route out of band. Session calls are admitted through the same queue: the route must exactly match this connection's current attachment.

要点Key points

  • 只有准入排队；调用结果在队列外等待，所以同一 Session 上的调用可以并发。Only admission is queued; results are awaited outside the queue, so calls on one Session run concurrently.
  • openingSessions 让并发的 attach 共享同一次打开；失败时一起失败，之后可以重试。openingSessions lets concurrent attaches share one open; on failure they fail together, and a later retry may succeed.
  • 打开期间服务器开始关闭：立即 handle.close() 并以 server_draining 拒绝。If the server starts closing during an open, handle.close() runs at once and the attach rejects with server_draining.

工作原理How it works

  1. 应用的管理服务调用 presentation.attachSession(sessionId, ctx)；结果里不带任何路由 id。The app's management service calls presentation.attachSession(sessionId, ctx); its result carries no route ids.
  2. 一个 Session 可以有多个连接的附着；每个附着各自有租约。One Session may have attachments from several connections, each with its own lease.
  3. 要彻底删除 Session，先调用 prepareSessionRemoval(sessionId)，再删应用自己的元数据。To delete a Session, call prepareSessionRemoval(sessionId) first, then delete the app's own metadata.

附着的结束How attachments end#

一句话结论Takeawaydetach、切换 Session、连接断开、句柄 terminated、prepareSessionRemoval() 和 Server.close() 最终都走 releaseAttachment()：同一附着只释放一次，先等已准入的调用结算，再 lease.release()，最后摘掉路由——只有 detach 与失效会推送 attachment: null。删除和关闭服务器还会 handle.close()。Detach, switching Sessions, a dropped connection, a terminated handle, prepareSessionRemoval() and Server.close() all end in releaseAttachment(): each attachment is released once, admitted calls settle first, then lease.release(), then the route is cleared; only detach and invalidation push attachment: null. Removal and shutdown also call handle.close().

要点Key points

  • 连接断开只释放附着，Session 仍被托管；什么时候让 worker 退役由应用决定。A dropped connection only releases the attachment; the Session stays hosted, and the app decides when its worker retires.
  • 句柄终止后 Session 从 hostedSessions 删除；下次 attach 会重新打开它。After a handle terminates, the Session leaves hostedSessions; the next attach reopens it.
  • 释放失败也一定清掉路由（finally），否则连接会永远占着它。The route is cleared even if release fails (finally); otherwise the connection would hold it forever.

工作原理How it works

  1. 在租约的 release(ctx) 里放掉 Session 级资源；它可能在调用仍在完成时被等待。Free Session-level resources in the lease's release(ctx); it may be awaited while calls are still completing.
  2. 用 terminated 报告 worker 意外退出，让客户端尽快看到 attachment: null。Report unexpected worker exits through terminated so clients see attachment: null quickly.
  3. 关闭失败时 server.close() 与 server.closed 以 AggregateError 拒绝。On cleanup failure server.close() and server.closed reject with an AggregateError.

Unix 监听器The Unix listener#

一句话结论TakeawayUnixListener.start() 建 0700 目录，清理陈旧 socket（还活着就拒绝启动），先在 bind-<sha256 前 8 位> 上监听，记下 socket 的 dev/ino，再用 link() 原子地发布到公共路径、chmod 0600、删掉 bind 路径。关闭时只删除身份仍然匹配的 socket，所以接替它的新服务器不会被误删。UnixListener.start() creates a 0700 directory, cleans up stale sockets (refusing to start if one is alive), listens first on bind-<first 8 hex of sha256>, records the socket's dev/ino, then publishes it atomically to the public path with link(), chmod 0600s it and unlinks the bind path. On close it removes the socket only while its identity still matches, so a server that replaced it is never removed by mistake.

要点Key points

  • 活性探测：连得上或 1000 ms 没反应都算“还活着”——宁可启动失败，也不删别人的 socket。Liveness probe: connecting, or no answer within 1000 ms, both count as alive; better to fail start-up than delete another server's socket.
  • 删除前总是先改名（stale- / cleanup-）再核对 dev/ino：避免与并发的替换竞争。Removal always renames first (stale- / cleanup-) and then checks dev/ino, to avoid racing a concurrent replacement.
  • UnixByteConnection 把排队字节限制在 maxPendingBytes（默认 4 × 帧上限，至少帧上限 + 4），超过就断开慢的对端。UnixByteConnection caps queued bytes at maxPendingBytes (4 × the frame limit by default, at least limit + 4) and drops a slow peer beyond it.

工作原理How it works

  1. getUnixSocketPath(serverId, dir) 得到 <dir>/<serverId>.sock；README 建议用一个短的私有运行时目录。getUnixSocketPath(serverId, dir) gives <dir>/<serverId>.sock; the README recommends a short private runtime directory.
  2. createUnixListener({ path, mode, maxPendingBytes, gracefulCloseTimeoutMs }) 可以和其它监听器一起交给 new Server()。createUnixListener({ path, mode, maxPendingBytes, gracefulCloseTimeoutMs }) can go to new Server() alongside other listeners.
  3. coding-agent：目录默认 ~/.pi/server，可用 PI_SERVER_DIR 覆盖。coding-agent: the directory defaults to ~/.pi/server, overridable with PI_SERVER_DIR.

一句话结论Takeaway能越过协议边界的错误都是 ServerError：五个子类覆盖 wrong_server、session_not_found、session_ambiguous、session_not_attached 和 server_draining，应用也可以用 Chord 的 RemoteServiceErrorCode。其它异常一律变成 internal_error "Internal server error"，细节只交给 onError。./testing 提供测试服务器、内存宿主与帧级协议客户端。Errors that may cross the protocol boundary are ServerErrors: five subclasses cover wrong_server, session_not_found, session_ambiguous, session_not_attached and server_draining, and apps may also use Chord's RemoteServiceErrorCodes. Any other exception becomes internal_error "Internal server error", with details only in onError. ./testing provides a test server, an in-memory host and a frame-level protocol client.

要点Key points

  • wrong_server 在访问任何仓库之前检查：发错服务器的请求不会触发 resolveSession。wrong_server is checked before any repository access: a request for another server never triggers resolveSession.
  • 只有 ServerError 与 RemoteServiceError 的消息会被转发；其它异常的消息和堆栈不会离开服务器。Only ServerError and RemoteServiceError messages are forwarded; other exceptions' messages and stacks never leave the server.
  • conformance.test.ts 是最大的测试文件：多附着、过期路由、未知 / 有歧义的 Session、Harness 终止与关闭时的清理。conformance.test.ts is the largest test file: multiple attachments, stale routes, unknown / ambiguous Sessions, Harness termination and shutdown cleanup.

工作原理How it works

  1. 在 resolveSession 里 throw new SessionNotFoundError() 或 new SessionAmbiguousError()。In resolveSession, throw new SessionNotFoundError() or new SessionAmbiguousError().
  2. const { server, host } = createTestServer({ listeners }) 得到一个未启动的测试服务器。const { server, host } = createTestServer({ listeners }) gives an unstarted test server.
  3. const c = await connectUnixTestClient(path)，用 ProtocolTestClient 按帧断言。const c = await connectUnixTestClient(path), then assert frame by frame with ProtocolTestClient.

测试Tests#

一句话结论Takeaway六个测试文件：conformance.test.ts（20 个用例）用 ./testing 覆盖 Session 协议——多附着、过期路由、跨服务器请求、未知 / 有歧义的 Session、Harness 终止与关闭时的清理；protocol.test.ts 覆盖握手与分帧（分片、合并、截断）；server.test.ts 覆盖选项校验、并发启动、握手超时与关闭失败；unix*.test.ts 与 listener.test.ts 覆盖 socket 绑定、陈旧清理、身份检查，以及排在待发数据之后的最终错误帧。Six test files: conformance.test.ts (20 cases) uses ./testing to cover the Session protocol: multiple attachments, stale routes, cross-server requests, unknown / ambiguous Sessions, Harness termination and shutdown cleanup; protocol.test.ts covers the handshake and framing (fragmented, coalesced, truncated); server.test.ts covers option checks, concurrent start, the handshake timeout and shutdown failures; unix*.test.ts and listener.test.ts cover socket binding, stale cleanup, identity checks, and a final error frame queued behind pending output.
