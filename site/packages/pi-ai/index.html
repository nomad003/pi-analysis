入口与打包Entry points and bundling#

一句话结论Takeaway导入路径决定打包体积：根入口只给核心类型与工厂；/providers/<id> 只带一个 provider 的目录，SDK 首次请求时才加载；/providers/all 带全部目录但 SDK 依旧懒加载；/api/<id> 会立即加载 SDK。The import path decides bundle size: the root entry gives core types and factories; /providers/<id> brings one provider's catalog and loads its SDK on first request; /providers/all bundles every catalog but SDKs stay lazy; /api/<id> loads the SDK eagerly.

要点Key points

  • 每个 API 都有一个 *.lazy.ts：lazyApi(() => import("./x.ts"))，provider 只引用这个包装。Every API has a *.lazy.ts: lazyApi(() => import("./x.ts")); providers only reference that wrapper.
  • /compat 保留旧的全局 API（stream、complete、getModel），已弃用。/compat keeps the old global API (stream, complete, getModel) and is deprecated.
  • bin: pi-ai 提供 CLI（OAuth 登录、模型列表）。bin: pi-ai ships a CLI (OAuth login, model listing).

工作原理How it works

  1. 应用导入 builtinModels() 或若干 xxxProvider()。The app imports builtinModels() or a few xxxProvider() factories.
  2. createProvider({ api: anthropicMessagesApi() }) 只保存懒包装。createProvider({ api: anthropicMessagesApi() }) stores only the lazy wrapper.
  3. 第一次 stream 时 import() 实现模块（及其 SDK），之后由模块缓存去重。The first stream call import()s the implementation (and its SDK); the module cache dedupes later loads.

Models 与 ProviderModels and providers#

一句话结论TakeawayModels 是 provider 的集合，也是所有调用的门面：查模型同步完成，凭据存在 CredentialStore，动态目录通过 refresh() 先发布缓存、再联网更新。createProvider() 把一个或多个 API 实现、图像与分类器能力组装成 Provider。Models is a collection of providers and the facade for every call: model lookup is synchronous, credentials live in a CredentialStore, and dynamic catalogs refresh() by publishing the cache first and then updating from the network. createProvider() assembles one or more API implementations plus image and classifier capabilities into a Provider.

要点Key points

  • 一个 provider 可以按 model.api 分派到多个 API（如 Fireworks 同时用 OpenAI 与 Anthropic 兼容 API）。One provider can dispatch to several APIs by model.api (e.g. Fireworks uses both OpenAI- and Anthropic-compatible APIs).
  • 缺少对应 API 时 dispatch() 返回一个以 error 结束的流，而不是抛出。With no matching API, dispatch() returns a stream that ends in error instead of throwing.
  • getModels() 只返回对话模型；图像与分类器模型通过 getAllModels() 查到。getModels() returns chat models only; image and classifier models are found via getAllModels().

工作原理How it works

  1. createModels({ providers }) 构造 ModelsImpl，以 id 为键注册 provider。createModels({ providers }) builds a ModelsImpl keyed by provider id.
  2. refresh() 对每个有 fetchModels 的 provider 调用 refreshModels(ctx)。refresh() calls refreshModels(ctx) on every provider with fetchModels.
  3. 动态模型按 (type, id) 覆盖基线目录，getModels() 始终同步返回合并结果。Dynamic models override baseline entries by (type, id); getModels() always returns the merge synchronously.

一次 streamSimple 调用One streamSimple call#

一句话结论Takeawaymodels.streamSimple() 同步返回一个外层流，真正的工作（找 provider、解析认证、加载 API 模块、发请求）在它背后异步进行；任何一步失败都会变成外层流的最后一个 error 事件。models.streamSimple() returns an outer stream synchronously while the real work (find the provider, resolve auth, load the API module, send the request) happens behind it; a failure at any step becomes the outer stream's final error event.

要点Key points

  • 认证解析顺序：调用方的 apiKey 覆盖 → 已存凭据（OAuth 会先刷新）→ 环境变量。Auth resolution order: caller apiKey override → stored credential (OAuth refreshed first) → environment.
  • auth.baseUrl 会覆盖模型的 baseUrl（如企业网关）；transformHeaders 最后执行。auth.baseUrl overrides the model's baseUrl (e.g. enterprise gateways); transformHeaders runs last.
  • forwardStream() 把内层事件逐个转发，最后用内层的 result() 结束外层流。forwardStream() forwards inner events one by one and ends the outer stream with the inner result().

工作原理How it works

  1. normalizeContext(context) 同步生成 TranscriptContext。normalizeContext(context) builds a TranscriptContext synchronously.
  2. lazyStream(model, setup) 立即返回外层 AssistantMessageEventStream。lazyStream(model, setup) immediately returns the outer AssistantMessageEventStream.
  3. setup()：requireChatProvider → applyAuth → provider.streamSimple → dispatch → lazyApi 导入 → api.streamSimple。setup(): requireChatProvider → applyAuth → provider.streamSimple → dispatch → lazyApi import → api.streamSimple.
  4. 成功则转发；失败则 push 一个 { type: "error" } 并 end(message)。On success, forward; on failure, push { type: "error" } and end(message).

本节沿用第一版的图（原位于总览页），已按 v1.1.0 重新核对。This section keeps its first-edition diagram (formerly on the overview page), re-checked against v1.1.0.

事件语法与 EventStreamEvent grammar and EventStream#

一句话结论Takeaway每个响应都是 start → (内容块的 start/delta*/end)* → done | error，每个事件都带当前 partial。EventStream 是一个极小的推拉队列：生产者 push，消费者 for await，result() 在终止事件时 resolve。Every response is start → (block start / delta* / end)* → done | error, and every event carries the current partial. EventStream is a tiny push/pull queue: producers push, consumers for await, and result() resolves on the terminal event.

要点Key points

  • 7 种 StopReason：pending 只出现在 partial 上；deferred 表示异步任务，之后用 streamDeferred(handle) 取结果。Seven StopReasons: pending appears only on partials; deferred means an async job, fetched later with streamDeferred(handle).
  • 1.1.0：AssistantMessageEventStream 自动为最终消息写入 durationMs（单调时钟，从流创建开始计时）。1.1.0: AssistantMessageEventStream stamps durationMs on the final message (monotonic clock from stream creation).
  • 终止后 push 被忽略——迟到的事件不会污染已完成的消息。After termination, push is ignored — late events cannot corrupt a finished message.

工作原理How it works

  1. API 实现创建 AssistantMessageEventStream，边解析 SSE 边 push。API implementations create an AssistantMessageEventStream and push while parsing SSE.
  2. 有等待中的消费者就直接交付，否则进入 FIFO 队列。If a consumer is waiting, hand off directly; otherwise enqueue FIFO.
  3. done / error 时 isComplete 为真，result() 得到最终 AssistantMessage。On done / error, isComplete is true and result() yields the final AssistantMessage.

跨模型消息转换Cross-model message transform#

一句话结论Takeaway每次请求前，transformMessages() 把任意 provider 产生的历史改写成目标模型能接受的形式：降级图像、处理 thinking 签名、规范化工具调用 id、跳过失败消息、补齐孤立的工具结果。这就是会话中途换模型仍然可行的原因。Before every request, transformMessages() rewrites history produced by any provider into something the target model accepts: downgrade images, handle thinking signatures, normalize tool-call ids, skip failed messages, fill in orphaned tool results. This is why switching models mid-session works.

要点Key points

  • thinking 签名只在同一模型之间有效；跨模型时 thinking 转成普通文本，redacted thinking 直接丢弃。Thinking signatures are only valid on the same model; across models thinking becomes plain text and redacted thinking is dropped.
  • 工具调用 id 的映射同时应用到对应的 toolResult，保证配对关系不被破坏。The tool-call id map is applied to matching toolResults too, so pairs stay intact.
  • 没有结果的工具调用会得到合成的 isError 结果——多数 API 要求每个调用都有结果。Tool calls without a result get a synthesized isError result — most APIs require one per call.

工作原理How it works

  1. 各 API 的 convertMessages() 先调用 transformMessages(messages, model, normalizeToolCallId)。Each API's convertMessages() first calls transformMessages(messages, model, normalizeToolCallId).
  2. 然后才把统一消息映射成该 API 的请求格式。Only then are unified messages mapped to that API's request format.

思考等级、预算与成本Thinking levels, budgets and cost#

一句话结论Takeaway统一的思考等级 off … max 按模型裁剪；token 型 API 用默认预算表换算，并保证 maxTokens 留出至少 1024 个回答 token、不超过上下文窗口。每次响应的 Usage 都按模型目录价格（含分层与 1h 缓存写入）计算美元成本。Unified thinking levels off … max are clamped per model; token-budget APIs convert them with a default budget table while keeping maxTokens at least 1024 answer tokens and within the context window. Every response's Usage is priced in USD from the catalog (tiers and 1h cache writes included).

要点Key points

  • xhigh 与 max 只有在模型的 thinkingLevelMap 明确声明时才可用；null 表示该等级被禁用。xhigh and max exist only if the model's thinkingLevelMap declares them; null disables a level.
  • 分层定价：输入 token（含缓存）超过某层阈值时整次请求按该层计价。Tiered pricing: when input tokens (cache included) exceed a tier threshold, the whole request uses that tier.
  • isContextOverflow() 识别各家的“上下文过长”错误，coding-agent 据此压缩后重试。isContextOverflow() recognises each provider's context-overflow error; coding-agent compacts and retries on it.

工作原理How it works

  1. clampThinkingLevel(model, level) 找到最近的受支持等级。clampThinkingLevel(model, level) finds the nearest supported level.
  2. adjustMaxTokensForThinking + clampMaxTokensToContext 计算最终 maxTokens 与思考预算。adjustMaxTokensForThinking + clampMaxTokensToContext compute the final maxTokens and thinking budget.
  3. 响应结束时 calculateCost(model, usage) 填充 usage.cost。At the end of a response calculateCost(model, usage) fills usage.cost.
