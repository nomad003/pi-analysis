这个包是什么What this package ispi-tui 是一个独立的终端 UI 库：组件只需实现 render(width): string[]，TUI 把组件树渲染成行，再只把变化的部分写进终端。它自带两种屏幕（保留滚动历史的 regular 与备用屏 fullscreen）、Kitty 键盘协议、覆盖层、多行编辑器和自动补全。pi-tui is a standalone terminal UI library: a component only implements render(width): string[]; the TUI renders the tree to lines and writes only what changed. It ships two screens (regular, which keeps scrollback, and fullscreen on the alternate screen), the Kitty keyboard protocol, overlays, a multi-line editor and autocomplete.

没有 pi 内部依赖，pi-coding-agent 的 interactive 模式建立在它之上。共 19,409 行 TypeScript、18 个内置组件；package.json 没有 exports 字段，入口是 dist/index.js。No internal pi dependencies; pi-coding-agent's interactive mode is built on it. 19,409 lines of TypeScript and 18 built-in components; package.json has no exports map, the entry is dist/index.js.

模块结构Module structure#

一句话结论Takeaway四块：终端与输入（terminal.ts、stdin-buffer.ts、keys.ts）、渲染核心（tui.ts 与两种屏幕）、编辑（editor.ts 与自动补全）、文本与图形（宽度计算、Markdown、LaTeX、终端图片）。components/ 下是可直接使用的组件。Four blocks: terminal & input (terminal.ts, stdin-buffer.ts, keys.ts), the render core (tui.ts and the two screens), editing (editor.ts and autocomplete), and text & graphics (width maths, Markdown, LaTeX, terminal images). components/ holds ready-to-use components.

组件模型The component model#

一句话结论TakeawayComponent 只有一个必需的渲染方法：render(width) 返回字符串数组，每个元素是一行。没有虚拟 DOM、没有布局树——Container 把子组件的行依次拼起来，TUI 再对这些行做差分。Component has one required render method: render(width) returns an array of strings, one per line. No virtual DOM, no layout tree — Container concatenates its children's lines, and the TUI diffs those lines.

要点Key points

  • 每一行的可见宽度不能超过 width；超过时 TUI 抛错并写 pi-tui-crash.log，而不是让终端自动换行弄乱画面。No line may be wider than width; if one is, the TUI throws and writes pi-tui-crash.log instead of letting the terminal wrap and corrupt the screen.
  • 获得焦点的组件（Focusable.focused = true）在光标处输出零宽的 CURSOR_MARKER；TUI 找到它、删掉它，再把硬件光标移过去——输入法候选框因此出现在正确位置。The focused component (Focusable.focused = true) emits a zero-width CURSOR_MARKER at the cursor; the TUI finds it, strips it and moves the hardware cursor there — so IME candidate windows appear in the right place.
  • 每行末尾都追加 SEGMENT_RESET（重置样式并关闭超链接），一行的样式不会漏到下一行。SEGMENT_RESET (reset style, close hyperlinks) is appended to every line, so styles never leak into the next line.
  • wantsKeyRelease 默认 false：Kitty 协议的按键释放事件会被过滤，组件需要时再显式打开。wantsKeyRelease defaults to false: Kitty key-release events are filtered unless a component opts in.

工作原理How it works

  1. 实现 render(width)：用 visibleWidth() / truncateToWidth() 保证每行不超宽。Implement render(width): use visibleWidth() / truncateToWidth() so no line is too wide.
  2. 需要输入就实现 handleInput(data)，用 matchesKey(data, "ctrl+c") 等判断按键。For input, implement handleInput(data) and test keys with matchesKey(data, "ctrl+c") and friends.
  3. 缓存渲染结果时实现 invalidate()，主题变化时 TUI 会调用它。If you cache rendered output, implement invalidate(); the TUI calls it when the theme changes.

TUI 渲染TUI rendering#

一句话结论Takeawaypi-tui 的组件只需实现 render(width) → string[]；渲染器批量合并请求，每帧最多 16 ms 一次，只重写变化的行。A pi-tui component only implements render(width) → string[]; the renderer batches requests, caps frames at one per 16 ms, and rewrites only changed lines.

本节沿用第一版的图（原位于总览页），已按 v1.1.0 重新核对。This section keeps its first-edition diagram (formerly on the overview page), re-checked against v1.1.0.

要点Key points

  • Container 组合子组件；可选的 handleInput / handleMouse 处理输入。Container composes children; optional handleInput / handleMouse handle input.
  • 两种屏幕：TuiMainScreen（主屏，保留 scrollback）与 TuiAltScreen（备用屏全屏）。Two screens: TuiMainScreen (main buffer, keeps scrollback) and TuiAltScreen (alternate-screen fullscreen).
  • 内置组件：Editor、Input、Markdown、SelectList、Image、Loader、ScrollView、Stack 等。Built-in components: Editor, Input, Markdown, SelectList, Image, Loader, ScrollView, Stack and more.

工作原理How it works

  1. ProcessTerminal 用 StdinBuffer 把批量到达的输入拆成完整的按键序列，交给获得焦点的组件。ProcessTerminal uses StdinBuffer to split batched input into complete key sequences for the focused component.
  2. requestRender() 在 process.nextTick 中合并请求，scheduleRender() 保证两帧间隔 ≥ MIN_RENDER_INTERVAL_MS（16 ms）；force 会立即渲染。requestRender() coalesces on process.nextTick; scheduleRender() keeps frames ≥ MIN_RENDER_INTERVAL_MS (16 ms) apart; force renders immediately.
  3. TuiMainScreen.doRender() 合成 overlay 后与 previousLines 比较，在同步输出（CSI ?2026h）中只写出变化的行。TuiMainScreen.doRender() composites overlays, diffs against previousLines, and writes only changed lines inside synchronized output (CSI ?2026h).

差分渲染Differential rendering#

一句话结论TakeawayrequestRender() 不立即渲染：同一 tick 内的请求被合并，两帧之间至少间隔 16ms；按键则走 requestImmediateRender() 立即出帧。regular 屏幕按行比较新旧两帧，只重写第一处到最后一处变化之间的行，并且整个写入包在同步输出序列里。requestRender() does not render right away: requests in one tick are merged and frames are at least 16 ms apart; key presses use requestImmediateRender() for an immediate frame. The regular screen compares old and new frames line by line, rewrites only the lines from the first to the last change, and wraps the whole write in synchronized output.

要点Key points

  • 宽度变化、高度变化（Termux 除外）、内容变短（开启 clearOnShrink 时）以及变化发生在视口上方时，会清屏重绘——终端滚动区里已经滚出去的行无法原地修改。A width change, a height change (except on Termux), shrinking content (with clearOnShrink) or a change above the viewport triggers a full redraw — lines already scrolled into the terminal's history cannot be edited in place.
  • 只删了行时不重写任何内容，只清掉尾部多出来的行。If lines were only deleted, nothing is rewritten; the extra tail lines are just cleared.
  • Kitty 图片占多行：变化区间会扩大到覆盖整张图，避免半张图残留。Kitty images span several rows: the changed range widens to cover the whole image so no half-image remains.
  • TUI.fullRedraws 记录全量重绘次数，可用来检查组件是否引起了不必要的重绘。TUI.fullRedraws counts full redraws, handy for spotting components that cause needless redraws.

工作原理How it works

  1. 准备一帧：render(width) → compositeOverlays() → extractCursorPosition() → applyLineResets()。Prepare a frame: render(width) → compositeOverlays() → extractCursorPosition() → applyLineResets().
  2. 依次判断是否需要全量重绘（见图中 7 个判断）。Check, in order, whether a full redraw is needed (the seven checks in the figure).
  3. 否则移动光标到 firstChanged，逐行写到 lastChanged，每行先 \x1b[2K 清除。Otherwise move to firstChanged and write each line through lastChanged, clearing each with \x1b[2K first.
  4. 最后把硬件光标放到 CURSOR_MARKER 的位置。Finally place the hardware cursor where CURSOR_MARKER was.

两种屏幕：regular 与 fullscreenTwo screens: regular and fullscreen#

一句话结论Takeawayregular（TuiMainScreen）把内容写进终端自己的滚动区，退出后历史仍在；fullscreen（TuiAltScreen）进入备用屏，自己管理滚动、鼠标、选择与搜索，每帧按屏幕行比较。pi-coding-agent 默认用 fullscreen，可在设置里改为 regular。Regular (TuiMainScreen) writes into the terminal's own scrollback, so history survives exit; fullscreen (TuiAltScreen) switches to the alternate screen and manages scrolling, mouse, selection and search itself, diffing by screen row every frame. pi-coding-agent defaults to fullscreen; settings can switch it to regular.

要点Key points

  • 备用屏一帧依次经过：布局帧 → 搜索高亮 → 回到底部提示 → 覆盖层 → 选区 → 短暂提示 → 光标与行尾重置，最后只写变化的行。An alternate-screen frame goes through: layout frame → search highlights → jump-to-end pill → overlays → selection → flashes → cursor and line resets, then only changed rows are written.
  • 备用屏开启鼠标报告（?1000/?1002/?1003/?1004/?1006），滚轮带加速，选择后可通过 OSC 52 复制。The alternate screen enables mouse reporting (?1000/?1002/?1003/?1004/?1006), accelerated wheel scrolling, and copy via OSC 52 after a selection.
  • 布局用 HStack / VStack / ScrollView，支持 basis / grow / shrink；regular 屏幕不需要这些。Layout uses HStack / VStack / ScrollView with basis / grow / shrink; the regular screen does without.

工作原理How it works

  1. TuiAltScreen.start() 写 \x1b[?1049h 进入备用屏并开启鼠标。TuiAltScreen.start() writes \x1b[?1049h to enter the alternate screen and enables the mouse.
  2. doRender() 调 renderLayoutFrame(root, width, height) 得到布局与行。doRender() calls renderLayoutFrame(root, width, height) for the layout and lines.
  3. 与 previousScreen 逐行比较；尺寸变化时整屏重绘。Compare row by row with previousScreen; redraw the whole screen when the size changes.

输入与按键Input and keys#

一句话结论Takeawaystdin 的原始字节先由 StdinBuffer 拼成完整的转义序列，再经过 handleTerminalInput() 的 8 个步骤——终端回复、输入监听器、调试键、覆盖层焦点修复、按键释放过滤——最后才交给获得焦点的组件。Raw stdin bytes are first assembled into whole escape sequences by StdinBuffer, then pass the eight steps of handleTerminalInput() — terminal replies, input listeners, the debug key, overlay focus repair, key-release filtering — before reaching the focused component.

要点Key points

  • 单独的 ESC 要等 10ms 才能确定是 Escape 键而不是序列开头；SSH 下默认 100ms，可用 PI_TUI_ESC_TIMEOUT 调整。A lone ESC needs 10 ms to be sure it is the Escape key rather than the start of a sequence; 100 ms over SSH, adjustable with PI_TUI_ESC_TIMEOUT.
  • 启动时请求 Kitty 键盘协议（flags 7）；终端不回复时改用 modifyOtherKeys，这样 shift+enter 等组合键仍可区分。Start-up requests the Kitty keyboard protocol (flags 7); if the terminal stays silent it falls back to modifyOtherKeys so combos like shift+enter remain distinguishable.
  • 按键用语义 id 表示（tui.input.submit、tui.editor.undo …，共 47 个），默认键位可被用户覆盖。Keys are referred to by semantic ids (tui.input.submit, tui.editor.undo …, 47 in total), and users can override the default bindings.

工作原理How it works

  1. ProcessTerminal.start() 打开 raw 模式与括号粘贴，并发送协议查询。ProcessTerminal.start() enables raw mode and bracketed paste and sends the protocol queries.
  2. StdinBuffer 输出完整序列；括号粘贴内容作为一整段交付。StdinBuffer emits whole sequences; bracketed-paste content is delivered as one chunk.
  3. handleTerminalInput(data) 走完 8 步，调用 focused.handleInput(data)，再立即渲染。handleTerminalInput(data) runs the eight steps, calls focused.handleInput(data), then renders immediately.
  4. 组件里用 getKeybindings().matches(data, id) 或 matchesKey(data, "ctrl+c") 判断。Inside components, test with getKeybindings().matches(data, id) or matchesKey(data, "ctrl+c").

编辑器与自动补全The editor and autocomplete#

一句话结论TakeawayEditor 是一个完整的多行编辑器：状态是 { lines, cursorLine, cursorCol }，配有快照式撤销、Emacs 风格的 kill ring、最多 100 条历史和大段粘贴折叠。handleInput() 按固定顺序尝试 13 类按键；自动补全由可替换的 AutocompleteProvider 提供。Editor is a full multi-line editor: its state is { lines, cursorLine, cursorCol }, with snapshot undo, an Emacs-style kill ring, up to 100 history entries and folding of large pastes. handleInput() tries 13 kinds of keys in a fixed order; completions come from a swappable AutocompleteProvider.

要点Key points

  • 超过 10 行或 1000 字符的粘贴显示为 [paste #1 +42 lines] 这样的标记，提交时再换回原文——编辑器本身保持轻量。Pastes over 10 lines or 1000 characters show as markers like [paste #1 +42 lines] and expand back on submit — the editor itself stays light.
  • 内置的 CombinedAutocompleteProvider 处理三种情况：行首 / 的斜杠命令（模糊匹配）、@ 文件附件（用 fd 搜索，20ms 防抖）、Tab 路径补全。The built-in CombinedAutocompleteProvider covers three cases: / slash commands at line start (fuzzy matched), @ file attachments (searched with fd, 20 ms debounce), and Tab path completion.
  • 光标前一个字符是 \ 时，Enter 会删掉它并插入换行而不是提交——给不支持 shift+enter 的终端用。When the character before the cursor is \, Enter deletes it and inserts a newline instead of submitting — a workaround for terminals without shift+enter.

工作原理How it works

  1. handleInput(data)：跳转模式 → 括号粘贴 → ctrl+c 交给上层 → 撤销 → 补全菜单 → … → 提交 → 插入字符。handleInput(data): jump mode → bracketed paste → ctrl+c to the parent → undo → completion menu → … → submit → insert text.
  2. 输入触发字符后调用 provider.getSuggestions(lines, line, col, { signal })，结果显示在 SelectList 中。After a trigger character, provider.getSuggestions(lines, line, col, { signal }) runs and results show in a SelectList.
  3. 确认后 applyCompletion() 返回新的文本与光标位置。On confirm, applyCompletion() returns the new text and cursor position.

覆盖层Overlays#

一句话结论TakeawayshowOverlay(component, options) 把一个组件画在其他内容之上并返回 OverlayHandle。位置由 9 个锚点、偏移、百分比 row/col 和边距决定；每帧在 compositeOverlays() 中按列拼进底层行。覆盖层组成一个栈，关闭时焦点回到打开前的组件。showOverlay(component, options) draws a component on top of everything and returns an OverlayHandle. Position comes from nine anchors, offsets, percentage row/col and margins; every frame compositeOverlays() splices it into the base lines by column. Overlays form a stack, and closing one returns focus to whatever had it before.

要点Key points

  • 默认居中，宽度为 min(80, 可用宽度)；width / maxHeight / row / col 都接受数字或 "50%" 这样的百分比。Default: centred, width min(80, available); width / maxHeight / row / col accept a number or a percentage such as "50%".
  • visible(w, h) 每帧重新求值：终端变小时覆盖层可以自动隐藏，焦点也随之转移。visible(w, h) is re-evaluated every frame: an overlay can hide itself on small terminals, and focus moves accordingly.
  • nonCapturing: true 的覆盖层只显示、不抢焦点，适合状态提示。A nonCapturing: true overlay shows without taking focus — good for status pop-ups.

工作原理How it works

  1. showOverlay() 记下当前焦点为 preFocus，把覆盖层压栈并聚焦（nonCapturing 除外）。showOverlay() records the current focus as preFocus, pushes the overlay and focuses it (unless nonCapturing).
  2. 每帧：筛选可见的 → 解析宽度 → render(width) 并截到 maxHeight → 用实际高度解析 row/col → compositeLineAt()。Each frame: filter visible → resolve width → render(width) cut to maxHeight → resolve row/col with the real height → compositeLineAt().
  3. hide() 出栈，焦点交给下一个可见覆盖层或 preFocus。hide() pops it; focus goes to the next visible overlay or preFocus.

终端能力Terminal capabilities#

一句话结论TakeawayProcessTerminal 在启动时协商能力（raw 模式、括号粘贴、Kitty 键盘协议或 modifyOtherKeys），运行中用 OSC 序列设置标题、进度和程序状态、查询前景/背景色。图片协议、真彩色和超链接按环境变量识别终端后决定，并可用 PI_* 环境变量覆盖。ProcessTerminal negotiates capabilities at start-up (raw mode, bracketed paste, Kitty keyboard protocol or modifyOtherKeys) and at run time uses OSC sequences for the title, progress, program status and fg/bg colour queries. Image protocol, truecolor and hyperlinks are decided by recognising the terminal from env vars, with PI_* overrides.

要点Key points

  • 图片：kitty、ghostty、wezterm、warp 用 Kitty 图形协议，iTerm2 用自己的协议；tmux、screen 与其他终端不显示图片。Images: kitty, ghostty, wezterm and warp use the Kitty graphics protocol, iTerm2 its own; tmux, screen and other terminals show no images.
  • 超链接（OSC 8）只在确认支持的终端里开启，否则 URL 会被吞掉；tmux 下会实际探测是否转发。Hyperlinks (OSC 8) are enabled only where known to work, since otherwise the URL disappears; under tmux forwarding is actually probed.
  • DA 查询（\x1b[c）用作“查询结束”的哨兵：在它之前没收到 Kitty 回复，就说明终端不支持。The DA query (\x1b[c) is the end-of-queries sentinel: no Kitty reply before it means no support.

工作原理How it works

  1. start(onInput, onResize)：raw 模式 → ?2004h → Kitty 查询 → DA。start(onInput, onResize): raw mode → ?2004h → Kitty query → DA.
  2. detectCapabilities() 根据 TERM_PROGRAM、KITTY_WINDOW_ID、TMUX 等变量给出 images / trueColor / hyperlinks。detectCapabilities() derives images / trueColor / hyperlinks from TERM_PROGRAM, KITTY_WINDOW_ID, TMUX and similar variables.
  3. stop() 关闭各模式并恢复原来的 raw 状态。stop() turns the modes off and restores the previous raw state.
