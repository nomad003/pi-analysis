这个包是什么What this package ispi-client 是远程 pi 会话的客户端一端，且与传输无关：你给它一个 ByteTransportFactory，它负责握手（并核对物理端点报告的逻辑 serverId）、按 id 关联请求、取消、带外附着和带缓冲的服务订阅。它不构造类型化的服务代理——createClientServiceTransport() 把一个按需解析的路由适配成 Chord 的 RemoteServiceTransport，类型由应用的 Chord 绑定提供。它从不自动重连。pi-client is the client end of remote pi sessions, and transport-neutral: give it a ByteTransportFactory and it handles the handshake (checking the logical serverId the physical endpoint reports), id-correlated requests, cancellation, out-of-band attachments and buffered service subscriptions. It builds no typed service proxies: createClientServiceTransport() adapts a lazily resolved route into a Chord RemoteServiceTransport, and types come from the application's Chord bindings. It never reconnects on its own.

一个 Client、一个 Connection、一个可替换的传输One Client, one Connection, a pluggable transport#

一句话结论TakeawayClient（client.ts）面向调用方：请求、订阅、附着与监听器；它内部的 Connection（connection.ts）管状态机、握手和 ServerMessageDecoder；字节的进出全部经过 ByteTransport 契约（transport.ts）。unix.ts 是一个独立子路径，提供 Unix socket 传输与本机服务器发现。Client (client.ts) faces the caller: requests, subscriptions, attachments and listeners; its internal Connection (connection.ts) owns the state machine, the handshake and the ServerMessageDecoder; every byte goes through the ByteTransport contract (transport.ts). unix.ts is a separate subpath with a Unix-socket transport and local server discovery.

要点Key points

  • 根入口不碰 Node API：浏览器或 worker 也可以用，只要提供自己的传输（例如 WebSocket）。The root entry touches no Node APIs: a browser or worker can use it with its own transport (a WebSocket, say).
  • Client 只认 @earendil-works/chord 的服务控制调用（目录、订阅、退订）和状态解码器，不解释任何应用契约。Client knows only @earendil-works/chord's service-control calls (catalogue, subscribe, unsubscribe) and state decoder; it interprets no application contract.
  • coding-agent 里有两种传输：createUnixTransportFactory() 和 radius-relay.ts 的 WebSocket 中继传输。coding-agent uses two transports: createUnixTransportFactory() and the WebSocket relay transport in radius-relay.ts.

工作原理How it works

  1. const client = await Client.connect({ serverId, transportFactory })：失败时它会自己 dispose()。const client = await Client.connect({ serverId, transportFactory }): on failure it disposes itself.
  2. 低层调用：client.request({ serverId: client.serverId }, { serviceId, member, args })。A low-level call: client.request({ serverId: client.serverId }, { serviceId, member, args }).
  3. 类型化调用：把 createClientServiceTransport(client, getTarget) 交给 Chord 绑定。Typed calls: hand createClientServiceTransport(client, getTarget) to a Chord binding.

连接的三个状态Three connection states#

一句话结论TakeawayConnection 在 disconnected → connecting → connected 之间切换。每次 connect() 都是一次带新序号的尝试：调用工厂得到一个全新的传输，先发客户端 hello，再等待服务端 hello，并要求其中的 serverId 与期望值完全一致。任何失败、关闭或 disconnect() 都回到 disconnected。Connection moves between disconnected → connecting → connected. Every connect() is an attempt with a new sequence number: the factory builds a fresh transport, the client hello goes first, then the server hello must arrive with exactly the expected serverId. Any failure, close or disconnect() returns to disconnected.

要点Key points

  • 旧尝试的回调带着旧 id，被 #isCurrent(id) 过滤掉；工厂迟到返回的传输会被直接 close()。Callbacks from an old attempt carry its id and are filtered by #isCurrent(id); a transport the factory returns late is simply closed.
  • 握手前的数据、第一条不是 hello、握手后再来 hello / hello_error，都是协议错误。Data before the client hello, a first message other than hello, or another hello / hello_error after connecting are all protocol errors.
  • 进入 disconnected 时 Client 清空 hello 与附着、拒绝全部挂起请求、丢弃全部订阅，再通知 onConnectionStateChange。Entering disconnected, the Client clears hello and the attachment, rejects every pending request, drops every subscription, then notifies onConnectionStateChange.

工作原理How it works

  1. client.onConnectionStateChange(({ state, error }) => …) 观察状态；client.connectionState 读取当前值。Observe with client.onConnectionStateChange(({ state, error }) => …); read client.connectionState for the current value.
  2. maxFrameLength 必须是 1 到 0xffffffff 的安全整数，否则构造时抛 TypeError。maxFrameLength must be a safe integer from 1 to 0xffffffff, or the constructor throws a TypeError.
  3. 关闭时解码器 end()：残留半帧会变成截断错误，作为断开原因上报。On close the decoder end()s: a leftover partial frame becomes a truncation error, reported as the disconnect reason.

一个请求的一生The life of one request#

一句话结论Takeaway#request() 先过三道守卫（已 dispose、未连接、已 abort），通过后才分配 request-N 并登记到 #pendingRequests，再编码、发送。回应按 id 取回条目：ok: true 解析结果，ok: false 变成带 code 的 ServerError。abort 立即在本地拒绝，并在已发送时补发一条 cancel。#request() passes three guards first (disposed, not connected, already aborted), and only then allocates request-N, registers it in #pendingRequests, encodes and sends. A response takes the entry back by id: ok: true resolves the result, ok: false becomes a ServerError with a code. An abort rejects locally at once and, if the request was sent, follows up with a cancel.

要点Key points

  • 回应可以乱序到达；没有对应条目的回应是协议错误，会断开连接。Responses may arrive out of order; a response with no matching entry is a protocol error and drops the connection.
  • abort 之后条目留在表里，直到服务端的 cancelled 回应到来，所以那条回应不算“无主”。After an abort the entry stays until the server's cancelled response arrives, so that response is not an orphan.
  • 调用在发送前用 Chord 的 parseServiceCall() 校验；编码失败会取回条目并拒绝，什么也不发送。The call is validated with Chord's parseServiceCall() before sending; an encoding failure takes back the entry and rejects without sending anything.

工作原理How it works

  1. await client.request(target, call, signal)：signal 是普通的 AbortSignal。await client.request(target, call, signal): signal is an ordinary AbortSignal.
  2. client.serviceCatalogue(target) 是同一路径上的一个预置调用，结果用 parseServiceCatalogue() 校验。client.serviceCatalogue(target) is a preset call on the same path, checked with parseServiceCatalogue().
  3. 错误处理：catch (e) { if (e instanceof ServerError && e.code === "cancelled") … }。Error handling: catch (e) { if (e instanceof ServerError && e.code === "cancelled") … }.

订阅：先快照，后更新Subscriptions: snapshot first, then updates#

一句话结论TakeawaysubscribeService() 先登记一个 service-N 监听器（hydrated = false, ready = false），再发订阅请求。快照之前到达的更新原样缓存；快照解码后 hydrated = true 并解码积压；调用方装好快照、调用 start() 之后，缓冲的更新才按序交付。交付经 deliveryTail 串行，异步监听器也不会乱序。subscribeService() registers a service-N listener first (hydrated = false, ready = false), then sends the subscribe request. Updates arriving before the snapshot are cached raw; once the snapshot decodes, hydrated = true and the backlog is decoded; only after the caller installs the snapshot and calls start() do buffered updates flow, in order. Delivery is chained on deliveryTail, so async listeners stay ordered too.

要点Key points

  • 每个订阅有自己的 Chord 状态解码器（createServiceStateDecoder()）：快照和更新都经过它。Every subscription has its own Chord state decoder (createServiceStateDecoder()); snapshots and updates both go through it.
  • dispose() 只在仍连接且路由仍是当前路由时发退订；随后等待 deliveryTail 并清空缓冲。dispose() sends the unsubscribe only while connected and while the route is current; then it awaits deliveryTail and clears the buffers.
  • 断开时 #serviceListeners 整体清空；订阅不会自动恢复。On disconnect #serviceListeners is cleared wholesale; subscriptions are not restored.

工作原理How it works

  1. const sub = await client.subscribeService(target, serviceId, mode, listener)；装好 sub.snapshot 后调用 sub.start()。const sub = await client.subscribeService(target, serviceId, mode, listener); install sub.snapshot, then call sub.start().
  2. 监听器抛出的错误只交给 ClientOptions.onListenerError。Listener errors only reach ClientOptions.onListenerError.
  3. 通过 Chord 绑定使用时，activate 对应 start()、close 对应 dispose()。Through a Chord binding, activate maps to start() and close to dispose().

一句话结论Takeaway附着由服务器带外推送：attachment 信封里的 serverId 必须是本服务器，否则断开；三个字段都相同的更新被忽略，其余通知 onAttachmentChange。createClientServiceTransport(client, getTarget) 在每次调用时才求值 getTarget()，所以 Session 服务可以直接传 () => client.attachment。The server pushes attachments out of band: the serverId in an attachment envelope must be this server's or the connection drops; an update with all three fields equal is ignored, anything else notifies onAttachmentChange. createClientServiceTransport(client, getTarget) evaluates getTarget() on every call, so Session services can pass () => client.attachment directly.

  • #targetIsCurrent()：服务器级目标与 hello 的 serverId 比较，Session 目标与当前附着的三个字段比较。#targetIsCurrent(): a server target is compared with the hello's serverId, a Session target with all three fields of the current attachment.

工作原理How it works

字节传输契约与 Unix 实现The byte-transport contract and the Unix implementation#

一句话结论TakeawayByteTransport 只有 send(chunk): Promise<void> 和 close()；工厂收到 onData / onClose / onError 三个回调，每次连接尝试新建一个已认证的传输。UnixByteTransport 用一条 Promise 链保序，按 maxPendingBytes 限制排队字节，写入返回 false 时等待 drain。ByteTransport is just send(chunk): Promise<void> and close(); the factory receives three callbacks, onData / onClose / onError, and builds one authenticated transport per attempt. UnixByteTransport keeps order with a promise chain, caps queued bytes with maxPendingBytes, and waits for drain when a write returns false.

要点Key points

  • maxPendingBytes 默认是帧上限的 4 倍（64 MiB）；超过就拒绝这次 send，Connection 随之断开。maxPendingBytes defaults to 4 × the frame limit (64 MiB); beyond it the send rejects and the Connection drops.
  • 每个 chunk 都先 slice() 复制，调用方之后修改缓冲也不影响写出的字节。Every chunk is copied with slice() first, so later changes to the caller's buffer cannot affect what is written.
  • 失败的写不会堵住队列：#writeTail 吞掉错误，只有该次调用的 Promise 被拒绝。A failed write never blocks the queue: #writeTail swallows it, and only that call's promise rejects.

工作原理How it works

  1. createUnixTransportFactory({ path, maxPendingBytes })：path 不能为空，Windows 上不可用。createUnixTransportFactory({ path, maxPendingBytes }): the path must not be empty; unavailable on Windows.
  2. 自定义传输：实现 send / close，并且恰好调用一次 onClose 或 onError。A custom transport: implement send / close and call exactly one of onClose or onError.
  3. 两端配置相同的 maxFrameLength，并让 maxPendingBytes 至少容得下一帧。Configure the same maxFrameLength on both peers, with maxPendingBytes large enough for one frame.

发现本机服务器Discovering local servers#

一句话结论TakeawaydiscoverUnixServers({ directory }) 读一个目录，只保留名为 <serverId>.sock 且 serverId 是规范 UUIDv4 的条目，然后用最多 16 个工作者并发探测：确认是 socket、用一个临时 Client 完成握手（默认 1000 ms 超时），最后按 serverId 排序返回 { serverId, path }。discoverUnixServers({ directory }) reads a directory, keeps only entries named <serverId>.sock whose serverId is a canonical UUIDv4, then probes them with up to 16 concurrent workers: check it is a socket, complete a handshake with a temporary Client (1000 ms timeout by default), and return { serverId, path } sorted by serverId.

要点Key points

  • 只读：陈旧或无响应的 socket 只会被忽略，从不删除——清理归服务器端的监听器。Read-only: stale or unresponsive sockets are just ignored, never deleted; cleanup belongs to the server's listener.
  • 超时、协议错误、版本不符、无 cause 的断开以及 ENOENT / ECONNREFUSED / ECONNRESET / EPIPE / ETIMEDOUT 都算“不是这台服务器”。Timeouts, protocol errors, version mismatches, cause-less disconnects and ENOENT / ECONNREFUSED / ECONNRESET / EPIPE / ETIMEDOUT all count as “not this server”.
  • 其它错误让整个发现失败：第一个错误被记下，工作者停止领取新候选。Any other error fails discovery: the first one is remembered and workers stop taking candidates.

工作原理How it works

  1. const routes = await discoverUnixServers({ directory })，directory 用绝对路径，例如展开后的 ~/.pi/server。const routes = await discoverUnixServers({ directory }) with an absolute directory such as the expanded ~/.pi/server.
  2. timeoutMs 覆盖每次探测的超时（1 … 2,147,483,647）。timeoutMs overrides the per-probe timeout (1 … 2,147,483,647).
  3. 然后 Client.connect({ serverId: route.serverId, transportFactory: createUnixTransportFactory({ path: route.path }) })。Then Client.connect({ serverId: route.serverId, transportFactory: createUnixTransportFactory({ path: route.path }) }).

失败语义与恢复Failure semantics and recovery#

一句话结论Takeaway调用方会看到五种拒绝：ServerError（服务器拒绝，带 code）、DisconnectedError（没连上或连接断了，传输错误放在 cause）、ClientDisposedError、ProtocolValidationError（对端违反协议，并且断开）和 AbortError。Client 从不自动重连或重放：断开之后 reconnect()、重新 attach、重新订阅，只重放已知安全的操作——这是应用的策略。Callers see five kinds of rejection: ServerError (the server refused, with a code), DisconnectedError (not connected or the connection dropped; transport errors in cause), ClientDisposedError, ProtocolValidationError (the peer broke the protocol, and the connection drops) and AbortError. The Client never reconnects or replays on its own: after a disconnect, reconnect(), attach again, subscribe again, and replay only operations known to be safe; that is the application's policy.

要点Key points

  • 断开时挂起的请求在本地拒绝，但已被服务器接受的工作仍可能在远端完成。On disconnect pending requests reject locally, but work the server accepted may still complete remotely.
  • coding-agent 的 RadiusClientReconnect 就是这样一种应用策略：指数退避重连并重新附着原来的 Session。coding-agent's RadiusClientReconnect is one such application policy: reconnect with exponential backoff and reattach the same Session.
